Redis THP Splitting Experiment Dashboard

This dashboard visualizes results from Transparent Huge Page (THP) splitting experiments on Redis. Each row represents a different experiment configuration against the same Redis workload. Row 0 is the all-broken run where every tracked THP is split into 4 KB pages. Row 1 is the no-split baseline. Rows 2–31 each split only one hot key's THP while the rest stay intact, which lets us estimate how costly that one split is.

Section 1 — Runtime Overview (All 32 Rows)

Mean Redis benchmark runtime for each experiment row, with error bars (std dev across 3 trials). Row 0 = all-broken: every tracked THP is split into 4 KB pages. This is the slowest row (~20.7s test1), confirming that splitting THPs hurts Redis. Row 1 = baseline: no THPs are split, all 2 MiB huge pages remain intact (~17.8s test1, faster). Rows 2–31: only one hot key's THP is split while the rest stay intact, isolating that key's THP contribution. Blue bars = Test 1 (hotkey runtime only); orange bars = Test 2 (runtime + dTLB counter collection, which adds overhead).

Section 1b — Combined: Runtimes + dTLB Loads + dTLB Misses

All four key metrics on one chart. Blue line = Test 1 runtime (s), orange line = Test 2 runtime (s), both on the left Y-axis. Red bars = mean dTLB loads, green bars = mean dTLB misses, both on the right Y-axis (log scale). Row 0 (all-broken, every THP split) is slowest; row 1 (baseline, no splitting) is fastest. Rows 2–31 split only one hot key each.

Section 2 — Runtime Change vs Split-Key Access Count

Each dot is one split-only-key experiment (rows 2–31). The X-axis is how many times that key was accessed during the workload; the Y-axis is the runtime change (%) compared to row 1, the no-split baseline. Green dots are faster than baseline, while red dots are slower. The dashed horizontal line marks zero change.

Section 3 — dTLB Miss Analysis

Hardware dTLB (data Translation Lookaside Buffer) counters from Test 2. Bars show total dTLB loads and misses (averaged over 3 trials). The green line shows the miss rate (misses / loads). Higher miss rates indicate more address-translation overhead, which THP splitting can influence.

Section 4 — Access Count Distribution

How many of the 4095 Redis keys fall into each cold-to-hot access bucket during the no-split baseline run. Most keys are "cold" with single-digit or low double-digit access counts, while only a small tail becomes truly hot. The Y-axis uses a log scale so those hot-tail buckets stay visible next to the cold-key majority, and each bar is labeled with its exact key count.

Section 5 — Top 30 Hottest Keys by Access Count

The 30 most frequently accessed keys, sorted by access count. Blue bars show access count in the no-split baseline run. Green dots show runtime change (%) versus row 1 when that key was the only one whose THP was split. Values above zero mean splitting that key helped, while values below zero mean it hurt.

Section 6 — Summary Statistics

Key numbers at a glance: no-split baseline runtime, all-broken runtime, and the best/worst runtimes among the single-split-key experiments, for both Test 1 and Test 2.
